# Hermes：20 种交互卡片设计

版本：设计提案 1.0 · 2026-10-03

状态：20 类布局已接入 Android 3.7.4 试用版；本文件仍记录较完整的产品设计目标，具体交付边界见 archive/release-notes/RELEASE-3.7.4.md 和应用内协议。当前执行状态卡只核对进展，不提供通用暂停/继续；保存通过 Hermes 处理对话完成，未实现卡片内实时服务端回执或跨 Markdown/JSON 事务。预览中的人物、数字、日期、记录和操作结果均为示例，不代表真实数据或服务器执行。

## 设计目标

让用户先看懂“发生了什么、要我做什么”，再决定是否深入。首页不承担长报告的阅读任务；点开卡片后也优先展示选项、字段、步骤或证据，而不是立即展开全文。

工作、生活、学习、健康等是内容分类；确认、比较、清单、趋势等是交互类型，两者独立。同一种卡片可用于多个领域，同一事项在不同阶段可转换呈现方式。例如：需要澄清 → 比较方案 → 分工执行 → 阶段验收 → 形成复盘。事项 ID 保持不变，避免每次整理都创建一个重复事项。

Agent 从受支持的组件和操作中选择、组合内容；App 负责排版、交互、长度限制、状态反馈和兼容。Agent 不输出可执行页面、任意脚本或任意文件修改指令。

## 通用交互规范

- 首页默认：一种状态、一个短标题、一个核心可视结构、一个主要操作。最多再提供一个次要操作；批量列表中的逐项控件不计入页脚操作数。
- 标题目标为 12–22 个中文字符，最多两行；说明最多两行。数字、日期、负责人、选项优先独立展示，禁止把多件事塞进同一段摘要。涉及不同决策的问题应拆卡；同一事项的证据和历史保留关联。
- 预览采用较完整的卡片状态；实际首页可折叠为紧凑态，点击进入同一张卡的交互详情。主操作应尽量在首页可达，不以展开长文为前提。
- 每张卡支持：事项状态、生成时间、必要的数据截止时间、来源入口、相关事项入口。非关键元信息收进详情。
- 原文、解释和来源默认折叠；涉及判断的不确定性直接显示，不能藏在原文中。未知值显示“未提供”，不填零，不推测负责人、截止日或进度。
- “不确定”“暂不处理”“保留原记录”是有效选择；不能用强制二选一制造错误事实。
- 展开、切换、选取、填写和排序在本地完成。正式提交后显示“正在保存”；收到服务器确认才显示“已保存”。离线可保留草稿，必须说明“仅此设备，尚未同步”。
- 启动 Agent 时显示“已提交 / 处理中 / 待你补充 / 已完成 / 失败”。不把排队成功当作任务完成，不生成虚假的百分比或预计完成时间。
- 所有提交使用稳定操作 ID 防重；失败保留输入，可重试。同一事项跨设备修改时校验版本，有冲突先展示差异，不能静默覆盖。
- 外发消息、邀请、支付、删除等高影响动作不由普通卡片选择隐式触发。卡片可以准备草稿；真正执行时展示对象和内容，并遵守用户授权。
- 无障碍：支持系统字号、深浅色、读屏、至少 44dp 触控区；状态同时使用文字与形状，不能只靠颜色。

## 逐卡设计

### 01 · 澄清确认

**触发**：两条记录疑似重复、身份关系不明确，或结论缺少用户确认。不能把相似描述直接认作同一事项。

**示例**：“这两条是同一次场地安排吗？”上方分别显示“9/28 看场地”和“9/29 场地已选定”，下方给出“同一件事 / 两件事 / 暂不确定”。

**交互**：选择只改变本地选中态；提交后记录用户确认的关联。“同一件事”不自动表示任务完成，“暂不确定”保留两个记录并标为待核实。

**数据**：question、record_refs、choices、selected_choice、evidence_refs。提交依赖轻量的关系更新；涉及实体合并时另行展示范围和可撤销记录。

### 02 · 方案比较

**触发**：至少两个明确可行的候选方案，且有可比较的信息。

**示例**：先试点与直接推广，按范围、准备时间、待验证条件比较；移动端一屏最多两列，更多方案进入比较详情。

**交互**：点选方案后突出该列并显示选择摘要，“采用这个方向”保存决策。需要用户指定执行范围或预算的事项不能因选中方案直接开始执行。

**数据**：options、shared_dimensions、values、unknowns、selected_option。推荐理由须与事实分开，未知维度保留“待核实”。

### 03 · 重点排序

**触发**：用户主动指定本日重点，或同一天出现多个需要取舍的候选事项。

**示例**：会议决策、研究提纲、学习计划三个条目，以 1 / 2 / 3 表示优先级。

**交互**：移动端长按拖动，并提供无障碍上移、下移操作；预览用方向按钮。保存只更新用户的优先级，不修改原截止日期，也不把归档文件变成正在推进的任务。

**数据**：item_refs、ordered_ids、scope_date、origin（用户指定或建议）。用户已确认的排序不被下一轮 Cron 无声重排。

### 04 · 时间选择

**触发**：事项需要约定时间，用户已提供候选范围，或已授权的日历能提供空闲信息。

**示例**：从三个候选时段中选一个，再选 30 / 45 / 60 分钟。展示具体日期与时区，未核验日历的候选明确标注。

**交互**：先生成安排草稿。用户确认创建个人日程时，由程序再次核验冲突与权限后写入；邀请他人需要额外展示收件人和内容。日历不可用时可保存为 Hermes 提醒，不能伪装已写入日历。

**数据**：candidate_slots、duration、timezone、availability_checked_at、calendar_target、reminder_policy。时区不采用服务器时区的隐式默认值。

### 05 · 会议分工

**触发**：用户分享会议录音、讨论记录或微信聊天记录，且其中包含明确行动项或待确认的分工。

**示例**：三行事项，每行保留负责人、截止日和来源位置，不展示整段会议摘要。

**交互**：逐项修改负责人、日期，勾选要建立的待办，再确认。未识别负责人可保持“待分配”；相对日期必须根据会议时间解析并供核对。创建个人跟踪事项不等同于已经向对应人员派发消息。

**数据**：meeting_ref、action_items、assignee_refs、due_at、source_spans、confirmation。重复导入按来源 ID 和行动项 ID 提示合并。

### 06 · 待办清单

**触发**：一个已确认事项可以拆成具体、可验证的步骤。

**示例**：准备分享会的四个步骤；顶部“2 / 4”，底部显示尚未保存的变更。

**交互**：勾选直接更新本地草稿，提交后写回服务器。已完成步骤可撤回，并保留完成时间。必须由工具完成的步骤不能仅凭用户勾选冒充工具执行成功。

**数据**：steps（稳定 ID、标题、状态、完成时间）、completion_policy。百分比仅由真实步骤数量计算，且不代表整个项目的工作量完成比例。

### 07 · 阶段验收

**触发**：多阶段事项有明确阶段目标和交付条件。

**示例**：“需求确认 → 小范围试点 → 复盘推广”，当前阶段显示“验收材料已就绪”。

**交互**：展开当前交付物与验收条件，确认通过后推进到下一阶段；材料不足时请求补充。完成当前阶段不自动完成整个项目。

**数据**：milestones、active_milestone_id、acceptance_criteria、deliverable_refs、approved_by、approved_at。阶段进度来自已确认状态，不是 Agent 主观估计。

### 08 · 阻塞处理

**触发**：正在执行的事项有明确缺口或依赖，缺口确实阻止下一步。

**示例**：“比较已完成；缺一项交付时间；确认后才能形成建议。”只展示当前最有用的补充字段。

**交互**：用户填入缺失信息并提交，卡片变为“待核验”，核验通过才解除阻塞。如果仍缺信息，继续指出缺口；不能提交成功就变成已解决。

**数据**：dependency_refs、missing_fields、impact、submitted_values、verification_state。复杂补充可进入携带上下文的对话。

### 09 · 执行状态

**触发**：Agent 已实际接收任务，有可查询的运行 ID。

**示例**：“读取资料 已完成；整理差异 进行中；生成建议 等待”。没有可量化依据时只显示阶段和时间，不显示假进度条。

**交互**：打开已完成的中间结果；如果执行器支持暂停/继续则显示对应按钮，否则只能显示实际支持的取消或后台运行。预览的暂停/继续仅演示状态，当前 Hermes 是否支持要开发时核实。

**数据**：run_id、steps、run_state、supported_controls、last_heartbeat、partial_result_refs。App 进入后台、网络断开和 Agent 停止是不同状态。

### 10 · 成果验收

**触发**：报告、表格、研究摘要、方案等交付物已生成且可读取。

**示例**：文档图标、标题、两条验收要点，主要按钮“采用”，次要按钮“提修改”。

**交互**：查看交付物后可采用该版本，或在卡内写一句具体修改要求，启动新修订任务。采用只记录认可和当前版本，不意味着发布、发送或替换外部文件。

**数据**：artifact_ref、version、acceptance_checks、review_state、revision_request。旧版本和用户修改保留关联。

### 11 · 数据趋势

**触发**：存在有效的数值、统计口径、时间范围和来源。

**示例**：“按期完成率 82% · 较上周 +8 个百分点”，下方六期趋势及本期分子/分母。

**交互**：查看指标口径、各期值和本期构成；点击“分析原因”才启动 Agent 深入分析。没有对比基线就只展示当前值，不编趋势。

**数据**：metric_key、value、unit、numerator、denominator、period、baseline、series、source_refs。区分百分比变化与百分点变化；不把同时变化直接解释为因果。

### 12 · 变化提醒

**触发**：同一事项的已确认状态与新信息产生值得关注的差异。

**示例**：“交付时间：周三 → 周五”，下方简列两个可能受影响的事项。

**交互**：展开影响后选择接受变更或保留原计划。外部事实不能被“保留原计划”抹去；应同时保存新证据与用户处理决定。用户确认后才更新相应的内部计划。

**数据**：field_changes、old_revision、new_evidence、affected_refs、resolution。相同变化避免被早晚 Cron 重复提醒。

### 13 · 事件轨迹

**触发**：同一事件有多条带日期的进展，用户需要理解来龙去脉。

**示例**：需求提出、完成讨论、等待试点结果三个节点。没有记录的时间段不补成“无进展”。

**交互**：点击节点展开原始依据；“补充进展”填写一条带时间的事实，保存为用户补充。新增进展不强制创建新任务。

**数据**：event_id、entries（发生时间、记录时间、事实、来源）、uncertainty。事件发生时间与归档时间分开。

### 14 · 证据分析

**触发**：用户提出研究、判断或比较问题，结论需要可核对的依据。

**示例**：一句暂定结论，下方“已有依据”和“仍待验证”两个区域；每条证据可查看来源和摘录。

**交互**：展开特定证据、指出不相关来源，或针对一个缺口继续研究。后续研究更新同一问题的证据集，保留结论变化原因。

**数据**：claim、supporting_evidence、counter_evidence、open_questions、source_refs。结论、原始事实与 Agent 推断分开；不显示未经校准的“置信度 92%”。

### 15 · 文稿修订

**触发**：用户要求润色或修改已有文本，且原稿和修改稿均可定位。

**示例**：一处删除、一处替换，以短段落和逐条接受开关显示，避免整篇旧稿和新稿重复堆叠。

**交互**：接受部分修改，保留其他原文，预览合并结果再保存为新版本；写回前检查原稿是否已改变。

**数据**：document_ref、base_revision、patches、accepted_patch_ids、output_ref。大文档进入专门编辑页面；卡片只处理当前片段。

### 16 · 资料分拣

**触发**：收到用户主动分享的微信记录、文件、图片或录音，且数据已经成功导入并可解析。

**示例**：三条资料，每条可选“归档资料 / 任务线索 / 暂不处理”。文件名、类型与读取状态保持可见。

**交互**：分类保存到指定位置；“任务线索”进入待确认区，不直接建立当前任务。导入失败提供重新选择或补充文本的入口，不能把“接收成功”显示为“已传入对话”。

**数据**：import_id、asset_refs、parse_state、suggested_classification、user_classification、destination_ref。原始文件和解析结果关联；不把历史目录误判为持续工作。

### 17 · 记忆变更

**触发**：依据用户明确表达保存长期事实或偏好后，展示可追溯的变更回执；或发现记忆冲突需要校正。

**示例**：“早间提醒时间 08:30 → 09:00”，附“来源：你刚才的设置”。

**交互**：可以纠正新值或撤销本次记忆变更。撤销记忆不自动撤销外部日历或 Cron；如涉及这些配置，应显示关联影响并单独处理。推断出的偏好必须作为建议待确认，不能包装成用户明确偏好。

**数据**：memory_ref、before、after、source_ref、change_reason、revision、reversible、linked_settings。涉及复杂 MD 更新需专门 writer 解析与定位，不能用字符串替换冒险修改。

### 18 · 人物跟进

**触发**：用户明确关联的人物存在未兑现承诺、计划联系或需要回顾的近期交集。

**示例**：“林同学 · 上次沟通 3 天前；已答应：分享阅读清单；待确定：下次讨论时间”。只使用有来源的信息。

**交互**：根据这次交集起草消息，用户可编辑复制；或创建自己的跟进提醒。默认不向对方发送，也不推断亲密度、性格或隐私属性。

**数据**：person_ref、recent_interaction_refs、commitments、followup_at、draft_ref。重名或身份不明先用澄清卡确认。

### 19 · 快速记录

**触发**：用户主动记录学习、阅读、日常事项等简单事实，或打开已选择的场景包。

**示例**：“今天阅读了多久？”用分钟步进器和一句可选备注，避免为了记录一个数字开启长对话。

**交互**：填写后直接保存为一条可撤销记录，显示发生时间。输入校验由程序负责；分析和长期总结另行进行，不强制每次调用模型。

**数据**：record_type、occurred_at、typed_fields、unit、note、source=user_input。场景包定义字段和单位，不允许 Agent 随意改变既有类型。

### 20 · 每日复盘

**触发**：晚间 Cron 完成整理，或用户手动开始复盘。早间可复用其摘要部分展示昨日延续事项，但不强迫再次填写。

**示例**：今天完成 3 项、待延续 1 项；用户勾选明日延续事项，写一句值得保留的心得。

**交互**：保存一份当日复盘版本和用户选定的延续项。未完成事项不自动重设截止日；明日重点是用户意向，和原任务状态分开。无数据时给出空态，不编造“今天完成很多”。

**数据**：date、completed_refs、carry_forward_refs、reflection_text、briefing_run_ref、revision。结构化摘要可查阅，完整叙述进入 Markdown 复盘档案。

## 模板之外的组合能力

20 种是首批完整模式，不是 20 个互不相通的页面。底层复用：短标题、状态、指标、趋势、字段、单选、多选、排序、时间、步骤、时间线、文件、差异、来源、短文本输入等组件。

允许“会议分工 + 一条待确认问题”“成果验收 + 证据入口”等有限组合。一张卡最多一个主要问题或主要操作流程；组合后过密就拆为关联卡。禁止根据模型输出任意嵌套组件，避免生成不可预测的页面。

## JSON、Skill 与 App 的职责

沿用用户已选的 Hermes 工作空间 + Markdown + JSON，不新建数据库，也不引入第二个 Agent。服务器保留权威数据，手机缓存已校验的快照与未提交草稿。文件的物理位置由工作空间配置确定，不在卡片内接受任意绝对路径。

| 层 | 职责 |
|---|---|
| App | 原生组件、输入校验、轻量交互、状态反馈、快照缓存、草稿恢复 |
| JSON 协议 | 稳定 ID、类型、字段、来源、动作描述、版本与时间 |
| 受约束 writer / 现有服务接口 | 校验写入范围、鉴权、防重、版本冲突、串行化写入、原子替换与恢复 |
| Hermes + Skill | 选择卡片、提炼内容、根据证据作判断、复杂处理、规范化生成 |
| Markdown | 长文、证据、过程记录、复盘与人可读档案 |
| Cron | 在配置的时区和早晚时间生成、更新卡片及简报索引 |

卡片的基础协议建议包含：`id`、`entity_id`、`revision`、`type`、`title`、`status`、`updated_at`、`source_refs`、`payload`、`actions`。每种 `type` 有独立字段约束；动作使用白名单类型与受验证参数，不能携带任意命令、可执行代码或不受控文件路径。

下面是拟议协议示例，不是可直接替换现有 3.7.3 数据的安装配置：

```json
{
  "presentation_version": 2,
  "id": "card-clarify-001",
  "entity_id": "event-venue-001",
  "revision": 4,
  "type": "clarification",
  "title": "这两条是同一次安排吗？",
  "status": "needs_confirmation",
  "payload": {
    "record_refs": ["record-001", "record-002"],
    "choices": [
      {"id": "same", "label": "同一件事"},
      {"id": "different", "label": "两件事"},
      {"id": "unknown", "label": "暂不确定"}
    ]
  },
  "actions": [
    {
      "id": "save-relation",
      "kind": "submit_choice",
      "label": "保存确认",
      "requires": ["selected_choice"],
      "effect": "update_relationship"
    }
  ]
}
```

动作请求附带操作 ID、事项 ID、卡片 ID、期望版本与输入值；服务端重新验证身份、能力、字段和对象范围，不能仅相信卡片描述。普通选择、记录、排序通过程序化写入即可；需要解释、推断、检索或生成才交给 Agent。

**实现前提**：当前 App 不能因为新增按钮就获得任意服务器写入能力。需要核实并扩展现有连接接口，或通过 Hermes 可调用的固定 writer 实现受控写入。若某项只能走对话，应明确显示“提交给 Hermes 处理”，而不能伪装成即时保存。这个增量能力属于现有连接方式的完善，不要求搭建独立数据库服务。

## 早晚 Cron 与累计记录

首次开启时，由 App 收集时区、早晚时间、数据范围和卡片偏好，生成配置指令。Agent 安装或确认规范与 writer，创建或更新相应 Cron，返回任务 ID 和实际计划时间，App 读取验证。重试配置不能重复创建 Cron。

每次 Cron 对话重新载入同一规范和上次索引，以 `run_id` 保存本次简报；现有事项按 `entity_id` 更新，不把整段聊天逐字累加为新卡片。用户已确认的事实、优先级和完成状态优先保留；新增证据与旧决定冲突时生成变化提醒或澄清卡。

继续提供一个手机可同步的当前 JSON。历史简报以日期和运行 ID 关联，长文放 MD。不能无限追加到单一文件：沿用或明确升级当前读取大小限制，达到阈值后按月归档历史 JSON / MD，当前索引保留入口。现有 3.7.3 的 1 MiB / 200 张卡限制需纳入兼容设计。

手机刷新只读取已生成内容，不触发整次总结。服务器生成使用最近游标和已变化资料做增量整理；需要全文重建时单独标明。这样减少日常等待，同时不承诺复杂研究一定即时完成。

## 兼容、恢复和边界状态

- 新协议先发布能力声明，Agent 只生成客户端支持的类型和动作。旧版客户端继续读取兼容快照；不直接把新类型塞进旧解析器。
- 不支持的卡片回退为短标题、状态、摘要与“查看详情”；保存原始数据供升级后读取。不能回退成首页长文本。
- 格式不合法时保留最近一次可用快照，并显示更新时间及本次同步失败；不要清空所有卡片。
- 单一写入者或文件锁 + 临时文件 + 校验 + 原子替换 + 版本日志；JSON 与 MD 的跨文件更新通过操作日志恢复，不能假设多个文件一起原子提交。
- 删除、撤销、重试、重复 Cron、重复导入、账号/服务器切换、来源越界、离线修改冲突均需有确定行为。不同连接的缓存与未提交操作隔离。
- 没有任何来源时显示真实空态；已归档资料只有用户明确指定用途，或有充分当前证据时才成为行动建议。

## 实施顺序与验收

先把完整 20 类协议和动作语义定下来，再按依赖分批落地，避免先画 20 张漂亮但不可执行的卡片。

1. **统一基础**：组件渲染、能力声明、长度限制、来源折叠、缓存、版本和动作回执；完成首次配置与 Cron 回读验证。
2. **高频闭环**：澄清确认、方案比较、会议分工、待办清单、资料分拣、记忆变更、每日复盘、成果验收。
3. **结构化操作**：重点排序、时间选择、阶段验收、阻塞处理、事件轨迹、人物跟进、快速记录。
4. **依赖更多能力**：执行状态、数据趋势、变化提醒、证据分析、文稿修订。执行控制必须以 Hermes 真正提供的能力为准。

验收至少覆盖：20 类都能在移动端大字号显示；首页无多段长正文；每个按钮有准确的动作结果；来源与不确定性可核对；离线不冒充保存成功；连续早晚运行无重复卡；重试无重复写入；并发冲突不丢数据；旧版客户端可安全读取或明确提示升级。正式开发还需在真实服务器和 Android 设备上验证，不以本次浏览器交互预览替代。
